常态化协作（git 拉取模式）

2026-09-21 起：推工蜂 → 打 tag → adata 从工蜂拉
部署动作仍需你说「部署」
  • 本地改代码，起 SQLite 服务自测；涉及 SQL / 建表 / 加列 / 加索引则按规则层第 09 节在 CVM 临时库 验
  • 开分支 → commit（中文描述）→ push → MR → 合入 adata-dev/main
  • 在 main 上打 release tag（如 v1.2）—— tag 即版本号，替代原来的 zip 命名
  • 让 CVM 拉该 tag 走查（需你确认「部署」）
  • 走查通过 → 让 adata 从工蜂拉同一个 tag 部署（需你确认「部署」）
  • 部署后核对：health 200 / 数据量与部署前一致 / 关键功能可用
流程变更（2026-09-21）：原「打包 zip 上传 adata → webapp update」改为「推工蜂 → adata 从工蜂拉取」。单一真相源变成 git 仓库，版本即 tag，不再有"部署包与仓库代码不一致"的风险；zip 打包约定随之作废。
DB 绑定：改为 git 拉取后 bound_db_names 通常转为 adata 平台的一次性配置，但首次部署或换库必须确认已绑定；若平台仍要求每次指定，部署仍须带齐 server_name / port / bound_db_names。漏绑会导致数据库绑定丢失。
连接机制（不变）：adata 上仍是运行时直连真实生产 MySQL —— 平台注入连接地址 → 适配层补全凭据 → SQL 自动翻译（表名加 agent_ 前缀）→ 建表幂等（表存在则跳过），部署不会清空或重建任何已有数据。
本清单是落地记录，执行状态随进展更新（阶段 0–3 已完成，阶段 4 为当前循环）。规则本身的长期定义见《协作SOP》。
最近更新：2026-09-21 —— 部署方式由「打包 zip 上传」改为「推工蜂 + adata 从工蜂拉」，版本管理改用 git tag。
