01三个环境的职责边界

同一份代码在三处运行，只用环境变量区分行为；职责不重叠、不交叉

环境角色定位什么时候用能做什么不能做什么
本地 macOS 开发 日常写代码、改逻辑、调 UI 用任意强模型开发；随意破坏重来 直接连 adata 真实库；跳过走查直接部署
CVM 走查验收 本地开发完、准备上生产前 用与生产同构的 MySQL 验证 SQL/迁移问题 当作第二生产环境长期使用；自己产生正式业务数据
adata 生产 走查通过后 承载真实用户与业务数据 直接改代码调试；用作开发沙盒

02触发条件 —— 什么情况下做什么

"什么时间"不是固定周期，是按事件触发

当：日常改 UI / 业务逻辑
在本地用 SQLite（不设 USER_MYSQL_HOST），秒起秒验证
当：新写 SQL / 加表 / 加索引
在 CVM 临时空库 验证（流程见第 09 节），SQLite 测不出方言差异
当：功能已在本地验证通过
commit → push → MR 到 adata-dev 仓库的 main，合并后打 release tag，再让 CVM 拉该 tag 走查
当：CVM 走查确认无误
让 adata 从工蜂拉取同一个 tag 部署，必须你明确说「部署」才执行
当：需要真实数据参考
从 adata 导出快照，灌入 CVM / 本地，不直连生产库
当：不确定某段代码能不能动
先查是否命中"禁止修改清单"（db-adapter / 认证 / 路径常量等）

03数据流向铁律

这一节讲的是 CVM / 本地 如何获取参考数据；adata 自己接收部署时走的是另一套直连机制，见下方补充说明

adata（真相源）
→ 导出 →
快照文件
→ 灌入 →
CVM / 本地
禁止反向 · 禁止 CVM↔本地互相同步
1
单向

数据只能从 adata 往外导（快照），任何环境都不能把数据推回 adata

2
隔离

CVM 和本地各自拉自己的快照，两者之间不同步，避免出现"哪份才是权威"的混乱

3
可追溯

快照文件按日期命名（如 snapshot-20260918.json），历史快照保留不覆盖

补充：新代码部署到 adata 后如何连接生产库（不经过快照，是直连）
代码上传时带 bound_db_names 参数 → adata 平台自动把连接地址注入容器环境变量 → 适配层用代码内置的默认账号密码补全连接信息 → 容器启动直连 adata 真实生产 MySQL（本体，非复印件）→ 运行时把代码里的 SQLite 写法自动翻译成 MySQL 写法（表名自动加 agent_ 前缀）→ 建表逻辑幂等（表已存在则跳过），部署新代码不会清空或重建任何已有数据。
bound_db_names→ 平台注入连接地址→ 默认账号密码补全→ 直连生产MySQL→ 语法自动翻译→ 幂等建表不清空

工蜂仓库是唯一真相源 —— 本地只推代码，CVM 与 adata 都从工蜂拉同一个 tag，不再手工打包上传

禁止：本地代码直接跳过 CVM 走查部署到 adata —— SQL/迁移层问题只有在同构环境里才测得出
2026-09-21 起生效的流程变更
原流程是「打包 zip 上传 adata → webapp update」，现改为「推工蜂 → adata 从工蜂拉取」。 好处：①单一真相源（git 仓库），不再有"部署包与仓库代码不一致"的风险 ②版本即 git tag，可回溯、可 diff、可回滚 ③省掉打包环节。 zip 打包约定随之作废：adata发布包/ 只保留版本记录与检验清单，不再作为交付物。

05Git 分支职责

两个独立仓库各有一个 main，含义完全不同 —— 「main」是分支名，「adata 基线代码」是代码内容，二者不是二选一

仓库 · 分支用途谁能提交
adata-dev · main唯一开发主线，装的就是 adata 基线代码，本方案所有工作在此进行开发者本人 + AI 协助
tag v*.*发布版本：打在 main 上，标记一次可部署的发布点；CVM 与 adata 拉取同一个 tag发布时创建
feature/*单个功能分支，从 adata-dev/main 切出按需创建，完成后 MR 合并回主线
终版文件 · mainCVM 旧线历史归档，冻结，仅供回溯查证不再提交
术语说明
早期方案提到的 adata-baseline 分支从未建立、不存在（改为独立仓库方案后废弃）。后续一律称「adata-dev 仓库的 main」。
不直推 main 开分支 commit 中文描述 push 提 MR 审核后合并

07部署红线

1
先列命令

任何触达 CVM / adata 服务器的操作，必须先完整列出将执行的命令

2
明确指令才执行

等你说出「部署」两个字才真正执行，不自行推断

3
部署后核对

服务状态 online、健康检查 200、关键功能可用，三项缺一不可

4
绑定参数核对

改为 git 拉取后，bound_db_names 通常转为 adata 平台的一次性配置（绑库不随每次部署重传）。但首次部署或换库时必须确认已绑定；若平台仍要求每次指定，则部署仍须带齐 server_name / port / bound_db_names。漏绑或漏传会导致数据库绑定丢失，线上数据"消失"。

5
走查与生产同一 tag

CVM 走查和 adata 生产必须指向同一个 git tag，避免"验过的代码"与"上的代码"不是同一份

08数据安全规则

1
旧快照不删

每次导出的快照文件保留历史版本，方便回溯对比

2
原库先备份

CVM 现有 SQLite 数据库原地重命名归档，不直接删除或覆盖

3
灌库前核对

任何"灌快照"操作前，先确认目标库当前是否有独有数据需要单独保留

09MySQL 验收流程

部署到 adata 之前必须完成 —— SQLite 测不出 SQL 方言问题，而 adata 是生产环境，SQL 一挂就是全站 500

触发条件 —— 什么样的改动必须验

改动类型需要验？说明
纯前端 HTML / JS / 样式否不涉及数据库，SQLite 或本地直接看效果即可
server.js 业务逻辑（不动 SQL）否代码路径与数据库类型无关，SQLite 足够
server.js 里的 SQL 语句必须方言差异只有真实 MySQL 才暴露
建表 / 加列 / 加索引
initDatabase()		必须且必须用全新空库验 —— 表已存在时 IF NOT EXISTS 会跳过，测不出问题
db-adapter.js（翻译层）必须SQLite + MySQL 双验，改动影响两个方向
数据迁移脚本必须涉及真实数据写入，先在临时库跑通
为什么 SQLite 不够： 2026-09-18 实例 —— updated_by TEXT NOT NULL DEFAULT 'admin' 在 SQLite 完全合法、跑得好好的，但 MySQL 有条铁律"BLOB/TEXT/JSON 列不能有默认值"，导致整条 CREATE TABLE 失败。而适配层把该报错当作"表已存在"静默忽略，实际后果是全新 MySQL 库里一张业务表都建不出来。 这类问题在 SQLite 上根本不可能暴露，不是概率问题。

验收流程 —— 6 步

核心设计：在 CVM 上建临时库验证，绝不碰生产库

1
建临时库

CVM 上建 verify_YYYYMMDD，与正式库 topic_ip_cvm 完全隔离

2
跑初始化

新代码传到 /tmp/verify（不覆盖正式代码），用环境变量指向临时库跑一次 initDatabase()

3
核结构

核对表数量（应为 13 张）+ SHOW CREATE TABLE 抽查关键列定义是否符合预期

4
验迁移

若本次有新加列，单独验证 ALTER 路径 —— 确认 PRAGMA table_info 被正确翻译成查 INFORMATION_SCHEMA

5
冒烟

灌入数据 → 起服务 → 核心 API 跑一遍（活动列表、登录、活动类型）

6
清理

验完 DROP 临时库、删除临时目录，不留残余

两个已知局限（诚实说明，不粉饰）
① 版本差异（已确认，风险可控）：CVM 是 MySQL 8.0.46，adata 是 8.0.30-txsql（腾讯云 TencentDB）。两者同属 8.0 大版本，DDL 语法层面一致，CVM 上的验收结论对 adata 基本可信。需注意：txsql 是腾讯云自研分支，首次部署 adata 时仍应重点观察启动日志中的建表/迁移输出。
② 数据覆盖不全：CVM 用的是自身旧快照，adata 有更多活动记录。adata 独有那部分数据的数据特征（如某字段恰好为 null）在 CVM 这边验不到。这是"拿不到 adata 快照"留下的债，目前无解，属局部风险而非全站风险。
