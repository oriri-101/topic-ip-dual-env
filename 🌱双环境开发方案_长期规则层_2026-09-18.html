01三个环境的职责边界

同一份代码在三处运行，只用环境变量区分行为；职责不重叠、不交叉

环境角色定位什么时候用能做什么不能做什么
本地 macOS 开发 日常写代码、改逻辑、调 UI 用任意强模型开发；随意破坏重来 直接连 adata 真实库；跳过走查直接部署
CVM 走查验收 本地开发完、准备上生产前 用与生产同构的 MySQL 验证 SQL/迁移问题 当作第二生产环境长期使用；自己产生正式业务数据
adata 生产 走查通过后 承载真实用户与业务数据 直接改代码调试；用作开发沙盒

02触发条件 —— 什么情况下做什么

"什么时间"不是固定周期，是按事件触发

当：日常改 UI / 业务逻辑
在本地用 SQLite（不设 USER_MYSQL_HOST），秒起秒验证
当：新写 SQL / 加表 / 加索引
切到本地 Docker MySQL 验证，SQLite 测不出方言差异
当：功能已在本地验证通过
commit → push → MR 到 adata-baseline，合并后部署 CVM 走查
当：CVM 走查确认无误
打包部署到 adata，必须你明确说「部署」才执行
当：需要真实数据参考
从 adata 导出快照，灌入 CVM / 本地，不直连生产库
当：不确定某段代码能不能动
先查是否命中"禁止修改清单"（db-adapter / 认证 / 路径常量等）

03数据流向铁律

这一节讲的是 CVM / 本地 如何获取参考数据；adata 自己接收部署时走的是另一套直连机制，见下方补充说明

adata（真相源）
→ 导出 →
快照文件
→ 灌入 →
CVM / 本地
禁止反向 · 禁止 CVM↔本地互相同步
1
单向

数据只能从 adata 往外导（快照），任何环境都不能把数据推回 adata

2
隔离

CVM 和本地各自拉自己的快照，两者之间不同步，避免出现"哪份才是权威"的混乱

3
可追溯

快照文件按日期命名（如 snapshot-20260918.json），历史快照保留不覆盖

补充：新代码部署到 adata 后如何连接生产库（不经过快照，是直连）
代码上传时带 bound_db_names 参数 → adata 平台自动把连接地址注入容器环境变量 → 适配层用代码内置的默认账号密码补全连接信息 → 容器启动直连 adata 真实生产 MySQL（本体，非复印件）→ 运行时把代码里的 SQLite 写法自动翻译成 MySQL 写法（表名自动加 agent_ 前缀）→ 建表逻辑幂等（表已存在则跳过），部署新代码不会清空或重建任何已有数据。
bound_db_names→ 平台注入连接地址→ 默认账号密码补全→ 直连生产MySQL→ 语法自动翻译→ 幂等建表不清空

07部署红线

1
先列命令

任何触达 CVM / adata 服务器的操作，必须先完整列出将执行的命令

2
明确指令才执行

等你说出「部署」两个字才真正执行，不自行推断

3
部署后核对

服务状态 online、健康检查 200、关键功能可用，三项缺一不可

4
参数不漏

adata 部署必须带齐 server_name / port / bound_db_names，漏传最后一项会导致数据库绑定丢失

08数据安全规则

1
旧快照不删

每次导出的快照文件保留历史版本，方便回溯对比

2
原库先备份

CVM 现有 SQLite 数据库原地重命名归档，不直接删除或覆盖

3
灌库前核对

任何"灌快照"操作前，先确认目标库当前是否有独有数据需要单独保留

本文档是长期规则层，不随单次任务变化。如需调整规则本身（如新增环境、改变分支策略），需重新过一轮确认。
